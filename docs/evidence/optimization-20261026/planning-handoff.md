# 规划核验与事实补全交接

本文件描述 2026-10-26 的实现与验证边界。原始代码基线为 `d81410f6d77a8c1fcfb6cd18c2c4f239be8f3e9d`，最终测试结果以主任务串行集成运行记录为准。

## 核验为什么不会再删除景点？

`TripFactVerificationService` 只返回观察结果，不更改原景点。`TripService.reverify` 将结果写入 `quality.poi_verification`，区分 `verified`、`not_found`、`lookup_failed`。超时、限流、连接故障保留原内容；明确不存在也保留原内容，等待用户选择替代景点并确认。新名称、地址、位置等外部观察单独保存在 `observed`，不会冒充已经应用的修改。失败尝试有独立时间记录，不刷新此前成功核验时间。

## 用户如何继续处理？

工作台显示失败原因并提供重试；明确不存在的记录提供替换入口，导航到行程详情的 `replace_poi` 参数。替换的可信 POI 选择、预览与确认由主任务维护的 Result 页面承接。锁定和完成保护仍由 Java 最终写入规则控制。

## Java 与 Python 分别承担什么？

Java 核对已有时间轴、当天城市、实际交通方式、真实坐标、固定跨城交通、原城住宿接驳与整日预算，不把核验当成重新求解。Python 根据明确范围进行有界局部求解。双方消费 `planning-semantics-v1` 的事实有效期、未知路线、状态和整日预算定义；Java 包装资源与规范 JSON 的一致性由定向测试校验。

## 什么算事实已补齐？

由所有者提供来源、获取时间、有效期和明确核对声明。新增预约事实、提前到站要求、父子地点关系、自理餐饮地点四个集合，均被标记为 `user_declared`。已有营业窗口与住宿位置继续复用。来源名称或链接不等于系统独立验证官方信息；过期或矛盾事实不会使方案变成可行。

预约状态不会代替指定入场时段。存在固定预约时，须在“预订与费用”关联活动并填写固定时段或允许入场窗口。

## 提前到站时间是否只消除提醒？

不是。新鲜且确认的提前量会压缩出站前可用活动窗口，产生提前到站占时，纳入固定交通、原城接驳和整日预算。原 inline 交通 ID 保存成数据库 ID 后，兼容 `input_commitment_id`，避免用户已经补充的提前量失去关联。缺失或过期仍保留核验缺口。

## 餐厅获取不到时如何处理？

用户可以补充自理用餐的真实地点及来源，求解器为其预留用餐窗口和接驳。它是用户安排，不生成虚构餐厅，也不伪造价格或预订。明确用餐窗口仍为硬约束。

## 不同 POI 编号是否可以重复游览？

不能据此判断独立性。已确认包含关系的父子景点最多作为一份独立游览；声明为独立游览需要来源与有效期。疑似嵌套或关系过期会保留待核实状态。跨日包含关系也检查，局部改排不重写范围外日期的持久内容。

## 旧任务是否要全部重新扣费？

四个新增集合为空时，规范化阶段 hash 保持与原请求相同。非空新声明改变输入 hash。v3–v7 到 v8 只复用其余兼容字段相同的提供方事实、草稿和路线阶段；已经求解的旧时间轴不能直接复用。未对费用 Exactly Once 作保证。

## 已验证什么，还有什么待主任务验证？

六个直接受影响的 Python 模块定向运行 79 项通过；五项既有生成/API 集成路径因隔离 venv 缺少依赖而筛除。前端 `vue-tsc --noEmit` 通过。Java 新增无损核验、合同、事实校验与三项数据库依赖失效集成测试，由主任务统一串行运行 Maven，避免共享 target 的编译竞争。

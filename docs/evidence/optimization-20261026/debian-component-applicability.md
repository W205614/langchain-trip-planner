# Component applicability follow-up, 2026-10-26

This is independent source/package review, not a scan or runtime test. The image owner's final inventory and file evidence must bind any decision to its precise image ID. No Docker, CI, VEX or application changes were made.

## Perl: source package does not imply every binary contains both modules

Debian's [trixie amd64 perl-base file list](https://packages.debian.org/trixie/amd64/perl-base/filelist) does not contain `Pod/Text.pm` or `Archive/Tar.pm`. Both are instead listed under [perl-modules-5.40](https://packages.debian.org/trixie/all/perl-modules-5.40/filelist), at `/usr/share/perl/5.40.1/Pod/Text.pm` and `/usr/share/perl/5.40.1/Archive/Tar.pm`. These correspond to the documented vulnerable components for [CVE-2026-82560](https://security-tracker.debian.org/tracker/CVE-2026-82560) and [CVE-2026-9538](https://security-tracker.debian.org/tracker/CVE-2026-9538).

A narrowly scoped `vulnerable_code_not_present` assessment is supportable if the final image proves absence of both files, the modules package, and vendored/CPAN copies on all effective Perl module paths (including `PERL5LIB` and application additions). Checking only that `perl-base` is installed is insufficient. A failed module load plus filesystem/package inventory is stronger evidence. This would be a component-absence decision, not a claim that the installed Perl source revision has been patched. A later module install invalidates the condition.

## ncurses: remove the vulnerable command, verify copies and aliases

The [Debian CVE record](https://security-tracker.debian.org/tracker/CVE-2025-69720) places the fault in `analyze_string` in `progs/infocmp.c`. The [upstream December 13 entry](https://invisible-island.net/ncurses/NEWS.html#index-t20251213) identifies the `infocmp -i` bounds correction. Debian [ncurses-bin's file list](https://packages.debian.org/trixie/amd64/ncurses-bin/filelist) assigns `/usr/bin/infocmp` to the command package.

If final-image evidence establishes that this executable and any hard-linked/renamed or separately copied versions are absent, and the offending implementation is not incorporated elsewhere, the specific vulnerable CLI component is absent. Keeping `libncursesw6`, `libtinfo6`, or terminal database files does not by itself demonstrate inclusion of `progs/infocmp.c`. Source-package scanner matches should be calibrated per binary component. Merely promising not to execute an installed command is a weaker reachability argument. This review performed no removal and does not certify a particular resulting image.

## zlib: independent source evidence and a limit on the safety argument

The companion [source comparison](./zlib-source-comparison.json) records HTTPS downloads of Debian's [source descriptor](https://deb.debian.org/debian/pool/main/z/zlib/zlib_1.3.dfsg+really1.3.1-1.dsc), orig archive and packaging archive, SHA256 comparisons against the descriptor, and a byte comparison with upstream v1.3.1. The packaging `debian/patches/series` is empty. All four inspected `gzwrite.c`, `gzlib.c`, `gzread.c`, and `gzguts.h` files are identical. There was no independent GPG signer verification or final-image library-byte binding by this reviewer.

The [introducing commit 81cc0beb](https://github.com/madler/zlib/commit/81cc0bebedd935daeb81b0b6e475d8786b51af3d.patch) adds `state->again`, retry handling for a nonblocking stall and `gz_vacate`. Those are absent from the compared Debian/upstream 1.3.1 sources. The [fix df84af2](https://github.com/madler/zlib/commit/df84af25dc1942490e1d1c899a07619152a46148.patch) clears remaining input and resets the external input pointer following failed compression. These facts support that the installed source lacks the particular later implementation described in the CVE; they are independent of third-party issue comments.

However, an argument that older write errors make **all** later writes unreachable is incomplete. In [v1.3.1 gzwrite.c](https://raw.githubusercontent.com/madler/zlib/v1.3.1/gzwrite.c), lines 202–210 retain a caller buffer pointer if compression fails, lines 345–347 reject formatting while the error remains, and lines 362–364 derive the formatting address from the retained pointer. In [v1.3.1 gzlib.c](https://raw.githubusercontent.com/madler/zlib/v1.3.1/gzlib.c), `gzclearerr` at lines 475–490 accepts a writing handle and clears the error. A caller explicitly clearing a failed write and reusing that handle therefore requires separate analysis. This is an identified static counterexample to the broad error-latch proof, not a demonstrated exploit or a claim that the CVE's later `gz_vacate` overflow is reproduced unchanged.

The [Debian tracker](https://security-tracker.debian.org/tracker/CVE-2026-85091) still labels the installed source vulnerable, while describing the later affected version range. Keep that vendor status visible. The current independent evidence permits a precise statement about absent later code, but does not justify unqualified `not_affected` for every use of the system or vendored zlib. Before a product-specific exception, bind the actually loaded library hashes and source provenance, check separate wheels/bundled copies, and establish the relevant gz writer/error-recovery call behavior. A same-name package version alone is insufficient.
